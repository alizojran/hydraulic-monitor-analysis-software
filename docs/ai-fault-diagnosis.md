# AI 辅助故障识别 — 设计与实施文档

> 本文档描述 HMAS 集成 LLM（Claude）进行液压设备智能故障诊断的完整方案。  
> 目标里程碑：M4（生产化阶段）

---

## 一、核心设计原则

### 1.1 LLM 做什么，不做什么

| LLM 负责 | 应用层负责 |
|---|---|
| 综合多维证据推理 | 信号采集、FFT、轴承公式计算 |
| 自然语言诊断报告 | 基线偏差百分比计算 |
| 处置建议（换件 / 观察 / 停机）| 趋势斜率计算 |
| 历史经验摘要压缩 | 工况桶分类 |
| 置信度评估 | 规则引擎初判（faultClassifier）|

**原则：把数值计算和信号处理留在应用层，把"理解和推理"交给 LLM。**

LLM 的输入永远是**文字摘要**，不是原始数组。一段 300 token 的结构化描述比 4096 点 FFT 数组有效得多。

### 1.2 为什么不直接用通用 LLM

通用 LLM 有液压和振动的行业知识，但不了解：
- **这台具体设备**的正常振动水平
- **这台设备**历史上出现过什么问题
- **这个工厂**的运维习惯和风险偏好

解决办法不是微调模型（成本高、数据少），而是**每次调用时把设备档案注入 prompt**，让模型在当次会话中成为"了解这台设备的专家"。

## 二、设备档案结构

设备档案分三层，存储在 `localStorage`（或未来的后端数据库），每次诊断调用时全部注入 system prompt。

### 2.1 第一层：静态元数据（人工填写一次）

```
设备编号:     主泵 A01
品牌型号:     Rexroth A10VO45DFR/31R
安装日期:     2022-03-15
累计运行时长: [由系统自动累加]
轴承配置:
  - 位置: DE（驱动端）
    型号: SKF 6205-2Z
    几何参数: Bd=7.94mm, Pd=38.5mm, Nb=9, α=0°
  - 位置: NDE（非驱动端）
    型号: SKF 6205-2Z
    同上
额定参数:
  转速: 1480 rpm
  流量: 50 L/min
  最高压力: 280 bar
  工作油温范围: 40–65°C
安装环境: 室内，竖向安装，联轴器直连电机
备注: 夏季环境温度约35°C，冬季约5°C
```

这些字段在 ConfigView 新增"设备档案"Tab 中维护，存入 `persistedStore`（版本 `device-profile-v1`）。

### 2.2 第二层：工况基线库（系统自动建立）

**为什么需要按工况分桶：**  
同一台泵在 30% 负载时 RMS 可能是 0.12g，100% 负载时是 0.26g。如果只有一条基线，换了工况立刻失去参考价值。

**工况桶定义（可配置）：**

| 转速桶 | 范围 |
|---|---|
| LOW | < 600 rpm |
| MID | 600–1200 rpm |
| HIGH | > 1200 rpm |

| 负载桶 | 压力占额定比例 |
|---|---|
| LIGHT | < 40% |
| NOMINAL | 40–80% |
| HEAVY | > 80% |

共 3×3 = 9 个工况格子，每个格子存一条基线。实际中常用的可能只有 2–3 个。

**基线内容（每个工况桶）：**

```
工况: HIGH_NOMINAL（转速>1200rpm，负载40-80%）
采集时间: 2022-04-20（设备磨合后2个月）
振动 RMS: 0.18g
振动 Peak: 0.43g  
Crest Factor: 2.39
BPFI @ 87.2Hz: -68 dB
BPFO @ 58.1Hz: -71 dB
BSF  @ 34.6Hz: -74 dB
FTF  @ 6.5Hz:  -76 dB
压力脉动 RMS: 3.2 bar
油温: 58°C
说明: 健康基准，采集3次取平均
```

**建立基线的操作流程：**
1. 设备安装后磨合期（建议运行 200h 以上）完成后
2. 在已知健康状态下，选择典型工况（如额定转速+额定负载）稳定运行
3. 在频谱视图点击"建立基线"→ 系统采集 60s 数据，计算均值，存入对应工况桶
4. 如有多个常用工况，逐一建立

基线可以人工触发更新（如更换轴承后，应重建基线）。

### 2.3 第三层：历史事件日志（随时间自动积累）

每次完成诊断，系统自动追加一条记录。记录格式示例：

```yaml
- id: evt-2026-03-12-001
  timestamp: 2026-03-12T14:23:00
  trigger: manual  # manual / alarm / scheduled
  operating_condition: HIGH_NOMINAL
  measurements:
    rms: 0.42g
    rms_vs_baseline: +133%
    crest_factor: 4.8
    bpfi_amplitude: -42dB
    bpfi_vs_baseline: +26dB
    oil_temp: 62°C
  rule_engine_findings:
    - type: BPFI
      severity: warning
      amplitude_above_baseline_db: 26
  ai_diagnosis:
    conclusion: 内圈早期疲劳磨损
    confidence: medium
    recommendation: 4周后复查，如RMS超过0.60g立即安排检修
    reasoning_summary: BPFI超基线26dB，Crest Factor升至4.8，具有早期点蚀特征
  outcome:
    recorded_at: 2026-04-10T09:00:00
    actual_finding: 内圈点蚀（目视确认）
    diagnosis_correct: true
    action_taken: 更换SKF 6205-2Z轴承（DE侧）
    post_action_rms: 0.17g
    new_baseline_established: true
```

**反馈记录操作（UI）：**  
维修完成后，在"历史事件"列表找到对应记录 → 点击"记录结果" → 填写实际发现、是否更换部件、更换后的测量值。这是让档案持续学习的核心动作。

## 三、历史摘要的自动压缩

当历史事件超过 **20 条**（可配置），触发一次压缩：用 LLM 把原始日志转化为结构化摘要。

**压缩 prompt 示例：**

```
你是一名液压设备维护专家。以下是某设备的历史诊断事件记录（JSON格式）。
请将这些记录提炼为一段简洁的"设备经验摘要"，供后续诊断参考。

要求：
1. 指出该设备历史上出现过哪些类型的故障及发生频率
2. 总结各次诊断的准确性（LLM诊断与实际结果的对比）
3. 记录任何规律性特征（季节性、与运行时长的关系等）
4. 标注基线变更历史
5. 输出不超过400字

[历史事件JSON]
```

**压缩后存储的摘要示例：**

> 该设备（Rexroth A10VO45，主泵A01）截至2026年4月共记录诊断事件14次，实际发生故障3次：
> - 2024-09-15：外圈磨损（运行18个月，轴承更换后复查正常）
> - 2026-04-10：内圈点蚀（运行12个月，已更换，诊断正确）
> - 2025-07-03：密封件老化导致压力脉动异常（非轴承故障，AI漏判，规则引擎正确识别）
>
> AI诊断准确率：轴承故障识别12/14次正确；曾1次误报（2025-11，RMS升高实为联轴器对中偏差，非轴承）。
>
> 规律性特征：
> - 每年7–8月BPFI幅值较基线偏高约3–5dB，确认为热膨胀引起，非故障
> - 两次轴承故障均发生在运行约12–18个月时，建议在运行满12个月时安排预防性检查
>
> 当前基线版本：HIGH_NOMINAL基线建立于2026-04-11（第二次换轴承后）

## 四、诊断调用流程

### 4.1 触发方式

| 触发类型 | 时机 | 行为 |
|---|---|---|
| 手动 | 用户在频谱视图点击"AI 诊断"按钮 | 立即分析当前状态 |
| 告警驱动 | 高严重度告警（high/critical）触发 | 自动附加 AI 分析，显示在告警事件详情 |
| 定期报告 | 每周/每月报告生成时 | 作为报告的"AI 摘要"章节 |

### 4.2 发送给 LLM 的完整 prompt 结构

**System prompt（固定部分）：**

```
你是一名液压设备振动诊断专家，熟悉ISO 10816和ISO 13373振动监测标准，
以及轴承故障频率（BPFI/BPFO/BSF/FTF）诊断方法。

你的任务是根据提供的设备信息和测量数据，给出专业的故障诊断意见。

规则：
1. 只根据提供的数据推断，不编造数值
2. 明确区分"确定"和"可能"，不确定时说明需要进一步验证
3. 每个结论都给出具体的数据依据
4. 置信度分为：高（多项指标一致且有历史佐证）/ 中（部分指标异常）/ 低（数据不足或矛盾）
5. 建议措施必须具体可执行，不能只说"需要检查"
6. 输出使用结构化JSON，不要添加任何前缀说明

输出格式：
{
  "fault_type": "故障类型（如：内圈早期疲劳 / 外圈磨损 / 无异常 等）",
  "severity": "critical | warning | advisory | normal",
  "confidence": "high | medium | low",
  "evidence": ["证据1", "证据2", ...],
  "recommendation": "具体建议",
  "recheck_interval_days": 数字或null,
  "stop_machine": true或false,
  "explanation": "给现场工程师看的自然语言解释（2-4句）"
}
```

**User prompt（每次动态组装）：**

```
## 设备档案

设备：主泵A01（Rexroth A10VO45，安装于2022-03-15，已运行约3200小时）
轴承：SKF 6205-2Z × 2（DE + NDE），2026-04-10更换过DE侧
当前工况：HIGH_NOMINAL（转速1482rpm，压力218bar，油温61°C）

## 当前工况基线（参考）

健康基线（2026-04-11建立，换轴承后）：
- RMS: 0.17g | Peak: 0.41g | Crest Factor: 2.41
- BPFI: -69dB | BPFO: -72dB | BSF: -75dB | FTF: -77dB

## 当前测量值

- 振动 RMS: 0.24g（vs基线 +41%）
- Crest Factor: 3.1（vs基线 +29%）
- BPFI @ 87.2Hz: -61dB（vs基线 +8dB）⚠️
- BPFO @ 58.1Hz: -73dB（vs基线 -1dB，正常）
- BSF @ 34.6Hz: -74dB（正常）
- FTF @ 6.5Hz: -78dB（正常）
- 压力脉动RMS: 3.4bar（正常）
- 7天RMS趋势: 0.17 → 0.19 → 0.21 → 0.24（持续上升，日均+2%）

## 规则引擎初判

faultClassifier 结论：BPFI 幅值超过告警阈值（+8dB），疑似内圈异常

## 当前活跃告警

- V02振动RMS超限（warn级，持续2天）

## 设备历史摘要

[粘贴第三层的历史摘要文本]

## 请给出诊断意见
```

### 4.3 返回结果处理

LLM 返回 JSON 后，应用层做以下处理：

1. **解析 JSON**，提取 severity / confidence / recommendation
2. **展示到 UI**：在 FaultSummaryPanel 下方新增"AI 分析"区域，显示 explanation 和 recommendation
3. **自动追加到历史日志**：将本次诊断结果（含 ai_diagnosis 字段）写入事件日志
4. **触发告警**：如果 `stop_machine: true`，自动在告警流中创建 critical 级别事件
5. **等待反馈**：在事件记录上显示"待反馈"状态，直到用户填写实际结果

## 五、API 接入方案

### 5.1 推荐方案：用户自持 API Key

在 Config → 系统 Tab 增加"AI 配置"区域：

```
API 服务商:  [Anthropic Claude ▼]
API Key:     [sk-ant-... ●●●●●●●]  （AES加密存储在localStorage）
模型:        [claude-sonnet-4-6 ▼]
每月预算限额: [50] 美元（超出后禁用自动触发，手动仍可用）
```

**注意**：API Key 存储在浏览器 localStorage，安全性等同于密码管理器。对于企业生产部署，应改为服务端代理（见 5.2）。

### 5.2 企业部署方案：服务端代理

```
浏览器 HMAS
  → POST /api/diagnose { device_profile, measurements }
  → 内网 Node.js 代理服务（持有 API Key，不暴露给前端）
  → Anthropic API
  → 流式返回诊断结果
```

代理服务同时可以：
- 记录每次调用的 token 用量和成本
- 缓存相同设备同一天内的重复调用
- 审计日志（谁在何时对哪台设备做了诊断）

### 5.3 调用成本估算

每次诊断调用的 token 消耗：

| 部分 | 估算 token |
|---|---|
| System prompt | ~300 |
| 设备档案（静态+基线）| ~400 |
| 历史摘要 | ~300 |
| 当前测量数据 | ~250 |
| **输入合计** | **~1250** |
| 输出（JSON + explanation）| ~200 |
| **总计** | **~1450 token** |

以 claude-sonnet-4-6 定价约 **$0.003 / 次**。每天手动触发 5 次 + 1 次告警触发 = 约 $0.02/天 / 设备。10 台设备 × 30 天 = **约 $6/月**。

## 七、数据持久化设计

### 7.1 存储结构（localStorage keys）

| Key | 内容 | 版本 |
|---|---|---|
| `hmas-device-profile` | 静态元数据 + AI 配置 | v1 |
| `hmas-baselines` | 所有工况桶的基线 | v1 |
| `hmas-diagnostic-log` | 历史事件日志（最近 20 条原始 + 压缩摘要）| v1 |

### 7.2 诊断日志的存储策略

- 始终保留**最新 20 条**原始事件（完整 JSON）
- 第 21 条写入时，触发一次压缩 API 调用，将前 20 条压缩为摘要文本
- 摘要文本存入 `diagnostic-summary` 字段
- 原始的 20 条归档（可选：存为可下载的 JSON 文件）
- 如用户关闭 AI 功能，仅存规则引擎结果，不触发 API 调用

### 7.3 导出与迁移

设备档案、基线库、历史摘要均可作为一个 JSON 包导出：

```
[导出设备档案] → hmas-device-A01-2026-05-10.json
[导入设备档案] → 覆盖或合并到当前
```

设备更换或系统重装时，通过导入恢复设备历史知识，不从零开始。

## 八、实施步骤（建议顺序）

按依赖关系，建议分阶段实施：

### Phase 1 — 基础数据收集（无 LLM）

1. 在 ConfigView 新增"设备档案"Tab，实现静态元数据编辑和持久化
2. 实现工况基线库：基线建立、存储、按工况匹配
3. 实现基线偏差计算，在频谱视图显示"vs基线"百分比
4. 完善历史事件日志数据结构，确保每次告警记录足够的上下文

**验收标准**：用户能建立基线，频谱视图能显示"当前 RMS 超基线 +41%"

### Phase 2 — 诊断摘要生成（无 LLM）

5. 实现"诊断摘要生成器"：从当前测量 + 基线 + 告警 + 规则引擎结果，组装结构化文字摘要
6. 添加"AI 诊断"按钮，先只显示摘要（让用户看到"即将发给模型的数据"），无 API 调用

**验收标准**：点击"AI 诊断"显示一段格式化的设备状态摘要

### Phase 3 — LLM 接入

7. 实现 API Key 配置和加密存储
8. 实现 Claude API 调用（支持流式返回，实时显示诊断过程）
9. 解析 JSON 响应，渲染到 FaultSummaryPanel 下方的"AI 分析"卡片
10. 实现结果追加到历史事件日志

**验收标准**：端到端流程通：配置 Key → 点击诊断 → 显示 AI 结论

### Phase 4 — 反馈闭环

11. 实现维修结果反馈 UI（见 6.2）
12. 实现历史日志压缩（超过 20 条时自动触发）
13. 验证：填写反馈 → 下次诊断时 LLM 能在 prompt 中看到历史摘要

**验收标准**：诊断经过 3 次反馈后，摘要中能看到"AI 诊断正确率"类信息

## 九、风险与注意事项

| 风险 | 影响 | 对策 |
|---|---|---|
| LLM 过度自信 | 工程师误信错误诊断 | prompt 强制要求输出置信度；低置信度时 UI 加视觉警告 |
| 停机建议引起误操作 | 生产损失 | `stop_machine: true` 时 UI 显示二次确认弹窗，明确说明这是 AI 建议非自动执行 |
| API Key 泄露 | 账户被盗用 | 建议企业部署用服务端代理；个人用户使用低额度 Key + 月预算限制 |
